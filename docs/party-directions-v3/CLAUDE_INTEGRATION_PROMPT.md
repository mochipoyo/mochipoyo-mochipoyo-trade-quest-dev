# トレードクエスト：味方の戦闘用4方向画像を組み込む

添付の `TradeQuest_Party_Directions_v3.zip` を使って、主人公と全仲間の戦闘用画像を3Dテスト版へ実装してください。画像を作り直す依頼ではなく、同梱PNGの組み込み依頼です。現在のソースを読み、下記の参照時点から変更されていれば現行実装へ合わせてください。

- ブランチ：`feature/3d-full`
- テストURL：`https://raw.githack.com/mochipoyo/mochipoyo-mochipoyo-trade-quest-dev/feature/3d-full/3d/index.html`
- 調査日：2026-11-02。調査時に取得したブランチHEAD：`e007fd635ca9d6364b5bc85403018b8aa165d066`

## このパックに入っているもの

`sprites/<actorId>/{front,back,left,right}.png` の60枚。すべて320×320、RGBA透過PNG。

- 主人公＋既存固有画像のある仲間6人：正面7枚は既存PNGの描画画素をそのまま保持し、透明余白だけを追加。背面・左・右の21枚を新規制作。
- 固有画像がなかった仲間8人：正面・背面・左・右の32枚を新規制作。
- 合計：既存正面7枚＋新規53枚＝実装用60枚。
- `source_sheets/`：各人物の生成原寸シート15枚。既存キャラのシート左上にある生成版正面は比較資料であり、既存正面を勝手に置き換えない。
- `original_front/`：取得した正面PNG7枚の原本。主人公の原本は `assets/characters/jobs/warrior.png`。
- `manifest.json`：人物ID、旧sprite ID、方向別パス、基準点、画像ハッシュ、元シート切り出し範囲。
- `previews/index.html`：全員の4方向を確認できるローカルプレビュー。
- `integration/party-direction-resolver.mjs`：人物ID優先の参照モジュール。ゲームに適用済みのパッチではない。

今回の素材は15人の基本衣装。20職業×15人の着替えセットや、歩行・攻撃の連番アニメーションではない。存在しない職業画像を生成済みとして扱わない。

## 必ず守る見た目の条件

1. 顔、髪型、髪色、体格を人物の特徴として維持する。転職で別人に見える画像へ切り替えない。
2. 解決順序は「同じactor.id専用の明示的な職業別画像がある場合はそれ」→「同じactor.idの基本画像」。現在のパックは基本画像を全職業で使う。
3. `actor.job` や `actor.sprite` だけから別キャラ／汎用職業画像へ切り替えない。旧セーブでspriteが変更済みでも `actor.id` で本人へ戻す。
4. IDは `hero, lina, kyle, mina, seris, gald, lucia, elna, nagi, iris, sophia, io, ganes, aster, ord`。特にアステルは `aster`、イーリスは `iris`。名前の文字列や配列順で照合しない。
5. ルシアはコード上 `waveblade` だが、実際の既存立ち絵は紺髪・青い衣装・青い杖。本素材はその画像を優先している。職業名から剣士へ描き変えない。
6. 新規8人の髪型・装飾は人物設定を基に今回制作した外見。コードにその外見設定が以前から存在したとは説明しない。

## 現在の原因と修正箇所

調査時の `three-src/src/battle/BattleActors3D.js` では次の構造だった。

- `partyPixelBack(a)` は `Assets.walkFrame(a.sprite, 'up', 1)` → `Chars.frame(a.sprite, 'up', 0)` と進み、小さな歩行用の背面を戦闘へ拡大表示している。
- `partyPixelArt(a)` は立ち絵 → 歩行画像 → コード描画の順。左右配置でも正面の立ち絵が優先される。
- `buildSprite(ent)` が `buildArtVolume()` に渡して味方を表示する。
- `Actors.changeJob()` は `js/rpg/actors.js` 内で `a.sprite = JOBS[job].sprite` を実行する。

まず3D表示側で新しい人物ID→方向別画像の参照を追加し、上記の歩行画像より優先する。共有の転職処理やセーブ構造を変更する必要がなければ変更しない。

## 実装手順

1. PNG60枚を `assets/characters/party-directions-v3/sprites/<actorId>/<direction>.png` へ置く。`manifest.json` も同ディレクトリに置く。原寸シートやプレビューは実行時に読み込まない。
2. 現在のアセットURL基準を調査し、`3d/` からでも正しく参照する。manifest内のパスはパックルート相対。例えば実行ページが `/feature/3d-full/3d/index.html` なら、パックルートは `new URL('../assets/characters/party-directions-v3/', document.baseURI)` に相当する。ただし現行URL構造を確認すること。
3. `layout=front` の味方は `back.png`。`layout=side` で味方が右・敵が左なら `left.png`。逆側配置では `right.png`。`front` は正面確認・勝利等、意図した場面だけで使う。
4. `front/back/left/right` は画像上の向き。ワールド方位と混同しない。`up=back`, `down=front` の別名は必要時だけ使う。
5. 左右の画像はそれぞれ描いてあるため `flipX` や負のscaleで代用しない。既存の板の裏面が表画像の反転表示になることと、背面PNGを表示することを混同しない。カメラに見せる面へ選択済みの画像を正しく貼る。
6. 画像の透過を維持。`NearestFilter` と `imageSmoothingEnabled=false` を使い、縦横比を保持する。白背景を付けたり、色を一律に塗り替えたり、16×24へ縮小してから再拡大しない。
7. 320×320の透明余白を含むキャンバスと `pivot=[160,304]` を扱う。方向ごとに勝手に不透明領域だけへクロップすると、足元や大きさが変わる。既存 `cropPixels()` を通す場合はクロップ分だけpivotを補正し、全方向で同じ人物スケールを使う。
8. `referencePixelHeight` はその人物の4方向の最大可視高さ、`worldHeightRatio` は体格差の初期値。たとえば人物の基準ワールド高さを `H` とし、planeHeightを `320 / referencePixelHeight * H * worldHeightRatio` とすれば、主人公の元画像が小さいことだけで小人化しない。平面中央から足元までのオフセットは `(304/320 - 0.5) * planeHeight`。既存立体描画を使う場合も同じ考えで基準点を合わせる。UI・カメラに合わせて最終調整する。
9. 最初の戦闘前または編成変更時に、使用パーティの必要な方向を先読みする。画像URL単位のPromiseとテクスチャをキャッシュ。1フレームごとのダウンロード・ジオメトリ再生成をしない。
10. 読み込み中と失敗を分離する。新しい方向画像が読み込めたら、旧処理の4秒待ち条件で止めない。`kind` を増やすなら既存の待機条件も修正。初回の失敗を永久キャッシュせず、明示的に再試行可能にする。
11. 取得失敗時は同じ本人の既存画像か、従来のフォールバックへ戻し、欠損ID・URLをログに残す。別の仲間の画像へ置換しない。遅延ロード後には正しい画像へ復帰する。
12. 既存の被弾・点滅・消滅・詠唱・攻撃の時刻同期を維持する。画像は静止画なので、未作成のコマを無理に作った扱いにしない。既存の移動／拡縮／シェーダー演出を使う場合も画像を潰さない。
13. 2D版、主人公名、仲間加入条件、職業能力、装備、ストーリー、戦闘計算、既存セーブを維持する。今回の画像追加を理由にセーブを初期化しない。
14. `three-src/` の正規ビルド手順で生成物を更新する。ハッシュ付きの `3d/assets/main-*.js` だけを手編集しない。サービスワーカー／キャッシュがあれば新アセットへ更新されるか確認する。
